## 一、預算概況

### 💡 成本單位轉換（重要提示）

**1 單位 = 100 萬 Token**

本計劃的預算轉換：
```
總預算：    0.30 單位 = 300 萬 Token    ≈ $2-8 美金
預期成本：  0.12 單位 = 120 萬 Token    ≈ $1-3 美金
應急預留：  0.18 單位 = 180 萬 Token    ≈ $1-5 美金
```

**讀者需要知道的**：
- ✅ 成本是透明的：每消耗 100 萬 Token = 成本增加 0.01 單位
- ✅ 成本是便宜的：完整監控只需要幾美金
- ✅ 成本是可控的：預算限制和降級機制確保不超支

📍 **詳細成本參考**：見 memory 中的 `token_cost_reference.md`

---

### 1.1 預算三要素

```
╔═══════════════════════════════════════════════════════╗
║ 總預算    0.30 單位  ← 絕對上限，不能超過            ║
║           (300 萬 Token，約 $2-8)                     ║
║ 預期成本  0.12 單位  ← 根據歷史數據的估計              ║
║           (120 萬 Token，約 $1-3)                     ║
║ 應急預留  0.18 單位  ← 預留率 60%，用於應對變化        ║
║           (180 萬 Token，約 $1-5)                     ║
╚═══════════════════════════════════════════════════════╝
```

### 1.2 預留率说明

**為什麼要預留 60%？**

| 複雜度 | 預留率 | 理由 |
|--------|--------|------|
| 簡單（單個檢查） | 30% | 邏輯清晰，變數少 |
| 中等（多維度評估）| 50% | 有多個檢查維度，有互動 |
| **我們的任務** | **60%** | **涉及並行監控、網絡不確定性、實時數據流** |
| 複雜（多 Agent 對抗）| 70% | 有衝突解決、人工升級 |
| 超複雜（不可控因素多）| 80%+ | 涉及外部系統、用戶行為 |

**預留率的含義**：
- 預期成本 0.12 單位 = 我們最置信的估計
- 應急預留 0.18 單位 = 應對 6 種可能的變化
  - 網絡延遲（+10%）
  - API 限流（+15%）
  - 需要更多檢查維度（+20%）
  - 誤報率高導致重檢（+15%）
  - 等等...

## 二、成本分解

### 2.1 成本構成

**蜂群覺醒的成本由三部分組成**：

```
總成本 = 監控成本 + 檢測成本 + 預留
       = 0.10 + 0.02 + 0.18
       = 0.30 單位
```

### 2.2 監控成本（0.10 單位）

**成本驅動因素**：
- 股票數量：20 檔
- 檢查頻率：每 10 秒一次
- 檢查時間跨度：約 3 小時（代表性樣本）
- 模型等級：Haiku（輕量級）

**成本計算**：

| 項目 | 單位成本 | 數量 | 小計 |
|------|--------|------|------|
| 實時數據获取 | 0.00008 單位/檢查 | 1000 | 0.080 |
| 數據解析和轉換 | 0.00002 單位/檢查 | 1000 | 0.020 |
| **小計** | | | **0.100** |

**說明**：
- 1000 個檢查 ≈ 3 小時的監控
- 每個檢查包含：獲取 20 檔股票的實時數據 + 基礎轉換
- Haiku 模型的成本約為 Sonnet 的 1/4

### 2.3 檢測成本（0.02 單位）

**成本驅動因素**：
- 異常檢測維度：2 個（價格波動 + 成交量）
- 複雜度：簡單邏輯，沒有複雜計算
- 決策規則：5 條簡單的 if-then 邏輯

**成本計算**：

| 項目 | 單位成本 | 數量 | 小計 |
|------|--------|------|------|
| 波動檢測 | 0.00001 單位/檢查 | 1000 | 0.010 |
| 成交量檢測 | 0.00001 單位/檢查 | 1000 | 0.010 |
| **小計** | | | **0.020** |

**說明**：
- 檢測邏輯簡單，都是算術計算（百分比、比例）
- 沒有涉及複雜的機器學習或深度分析

### 2.4 應急預留（0.18 單位）

**預留的目的**：應對以下 6 種可能的成本增加

| 風險場景 | 影響成本 | 備註 |
|---------|--------|------|
| 網絡延遲導致重試 | +10% | API 超時，自動重試 |
| 誤報率高導致深度檢查 | +15% | 確認異常的準確性 |
| 需要增加檢查維度 | +20% | 例如加入技術指標 |
| 股票數量增加 | +10% | 從 20 檔擴展到 30 檔 |
| 檢查頻率提高 | +5% | 從 10 秒改為 5 秒 |
| 系統故障恢復 | +10% | 監控中斷後的追回檢查 |
| **最壞情況** | **~70%** | 所有風險同時發生 |

## 三、成本監控策略

### 3.1 實時監控表

執行過程中，根據以下表格監控成本：

```
╔════════════════════════════════════════════════════════════╗
║ 成本進度圖                                                   ║
║                                                             ║
║ 0.30 ├─────────────────────────────────────────┤ 停止點    ║
║      │                                           │          ║
║ 0.24 ├─────────────────────────────────┤ 臨界  │          ║
║      │  節省模式 >                      │  點   │          ║
║ 0.18 ├─────────────────────────┤ 警告│       │          ║
║      │                         │  線   │       │          ║
║ 0.12 ├─────────┤ 預期        │       │       │          ║
║      │         │ 成本         │       │       │          ║
║ 0    └─────────────────────────────────────────┘          ║
║      0%        40%            60%     80%    100%          ║
╚════════════════════════════════════════════════════════════╝
```

### 3.2 四個成本階段

| 階段 | 成本範圍 | 狀態 | 行動 | 備註 |
|------|---------|------|------|------|
| **正常** | 0 - 0.18 | 🟢 | 繼續全功能監控 | 預算充足，無需擔心 |
| **警告** | 0.18 - 0.24 | 🟡 | 進入節省模式 | 開始考慮成本優化 |
| **臨界** | 0.24 - 0.30 | 🔴 | 返回已有結果，停止新檢查 | 成本即將耗盡 |
| **超限** | > 0.30 | 🛑 | 立即停止所有檢查 | 絕對不能超過此點 |

### 3.3 四個成本階段的具體行動

#### 階段 1：正常運行（0 - 0.18）

**狀態指示**：🟢 綠燈

**監控內容**：
- ✅ 全部 20 檔股票
- ✅ 每 10 秒檢查一次
- ✅ 檢測所有定義的異常類型
- ✅ 完整的告警系統

**無需採取任何行動**，繼續運行。

**預期完成時間**：無限制（預算充足）

---

#### 階段 2：警告狀態（0.18 - 0.24）

**狀態指示**：🟡 黃燈（成本達到預期值）

**觸發條件**：
- 成本達到 0.18 單位
- 消耗了預期成本 100%
- 應急預留還有 50% 可用

**自動採取的行動**：

**行動 1：降低檢查頻率**
- 舊：每 10 秒檢查一次
- 新：每 30 秒檢查一次
- 效果：成本降低約 60%

**行動 2：繼續關鍵監控**
- 保持對 Critical 級別異常的檢測
- 可以暫停 Info 級別異常的檢測
- 確保不遺漏重大機會

**這個階段的目標**：用剩餘預留撐過執行週期

**預期持續時間**：10-30 分鐘（根據數據流量）

---

#### 階段 3：臨界點（0.24 - 0.30）

**狀態指示**：🔴 紅燈（成本接近上限）

**觸發條件**：
- 成本達到 0.24 單位
- 剩餘預算只有 0.06 單位
- 預留 33% 已經消耗

**自動採取的行動**：

**行動 1：立即停止低優先級檢查**
- ❌ 停止 Info 級別檢查
- ❌ 停止不常波動的股票監控
- ✅ 只保留 20 檔中最活躍的 10 檔

**行動 2：返回已有結果**
- 停止進一步的新檢查
- 將當前收集到的所有數據整理成報告
- 標記為「PARTIAL_COMPLETION」

**這個階段的目標**：極限節省成本，保護預算

**預期持續時間**：5-10 分鐘（快速關閉）

---

#### 階段 4：超限（> 0.30）

**狀態指示**：🛑 停止符

**這個情況不應該發生**，因為我們在階段 3 已經停止了。

**如果發生**（說明預估有誤）：
- 🛑 立即停止所有操作
- 🛑 返回已有數據（標記為「ERROR_BUDGET_EXCEEDED」）
- 📧 升級給項目經理
- 📊 分析為什麼超支（用於下次改進）

## 四、降級策略

### 4.1 什麼時候降級？

降級 = 簡化功能，但保留核心功能

**不升級給人工，而是自動簡化處理。**

### 4.2 三個降級級別

#### 降級 Level 1：降低檢查頻率

**觸發條件**：成本達到 0.18 單位（60%）

**具體做法**：
```
舊：每 10 秒檢查一次
新：每 30 秒檢查一次

公式：檢查頻率 ↓ 70% → 成本 ↓ 70%
成本從 0.12 / 天 降至 0.04 / 天
```

**影響**：
- ✅ 節省成本 70%（非常有效）
- ⚠️ 風險：可能遺漏快速波動（開盤前幾分鐘）

**何時用**：
- 預算快要用完
- 系統性能降低
- 市場波動平靜時期

---

#### 降級 Level 2：停止非關鍵檢查

**觸發條件**：成本達到 0.24 單位（80%）

**具體做法**：

**選項 A：停止低優先級異常檢測**
```
舊：檢測所有異常（波動 > 5%, 成交量 > 100% 等）
新：只檢測關鍵異常（波動 > 10%，漲停跌停）

成本削減：50%
```

**選項 B：停止低流動性股票的監控**
```
舊：監控全部 20 檔股票
新：只監控前 10 檔流動性最好的股票

成本削減：50%
```

**影響**：
- ✅ 節省成本 50%
- ⚠️ 風險：可能遺漏中等規模波動

**何時用**：
- 預算即將耗盡
- 只有最後一點預留
- 必須保證監控不中斷

---

#### 降級 Level 3：停止所有檢查，返回結果

**觸發條件**：成本超過 0.30 單位（100%）

**具體做法**：
1. 立即停止所有新的監控檢查
2. 將現有數據編譯成最終報告
3. 標記為「PARTIAL_COMPLETION」或「BUDGET_EXHAUSTED」
4. 不做任何進一步分析

**成本削減**：100%（完全停止）

**影響**：
- ✅ 預算不超支
- ⚠️ 風險：無法保證完整監控

**何時用**：
- 成本已經超支（預估有誤）
- 無法進一步優化
- 只能返回已有結果

---

### 4.3 降級的優先順序

**應該降級的優先順序**：

```
優先級 1（最後才降）：停止檢測 Info 級別異常
  ├─ Info 級別 = 波動 < 5% = 正常波動
  ├─ 不影響決策，只是統計信息
  └─ 削減成本 10-15%

優先級 2：停止監控低流動性股票
  ├─ 低流動性 = 交易量小、波動大
  ├─ 風險高，但概率小
  └─ 削減成本 20-30%

優先級 3（不得已才降）：降低檢查頻率
  ├─ 從 10 秒改為 30 秒
  ├─ 可能遺漏快速波動
  └─ 削減成本 60-70%

優先級 4（最後手段）：停止所有檢查
  ├─ 返回已有結果
  ├─ 放棄後續監控
  └─ 削減成本 100%（但功能喪失）
```

## 五、升級條件

### 5.1 什麼時候升級？

升級 = 停止自動處理，需要人工介入

**5 種升級場景**（見定義書中的詳細描述）

### 5.2 升級示例

#### 升級場景 1：誤報率過高

**條件**：誤報率 > 10%

**示例**：
```
一天 100 個告警，其中 15 個是誤報
→ 誤報率 = 15/100 = 15% > 10% ✗

升級給：系統管理員
要求：調整告警規則，降低誤報率
```

**升級信息**：
- 誤報數量和內容
- 誤報的規律（什麼時候多？）
- 建議的改進方案

#### 升級場景 2：檢測靈敏度異常低

**條件**：檢測靈敏度 < 90%

**示例**：
```
一天 20 個真實異常，只檢測到 16 個
→ 靈敏度 = 16/20 = 80% < 90% ✗

升級給：交易員或數據分析師
要求：分析漏報原因，改進檢測邏輯
```

**升級信息**：
- 漏報了哪些異常
- 為什麼漏報了？
- 怎麼改進才能不漏報

## 六、成本優化建議

### 6.1 根據執行結果調整

**執行完後的成本分析**：

```markdown
## 成本分析報告

執行時間：3 小時
預定成本：0.12 單位
實際成本：0.11 單位
偏差：-8.3%（低於預期）

分析：
- 網絡狀況良好，無需多次重試 ✅
- 誤報率低，無需深度檢查 ✅
- 股票數量 20 檔，接近最優規模 ✅

## 改進建議

### 短期改進（下次執行）
1. 降低預留率：60% → 50%（保留安全邊際）
2. 擴大監控範圍：20 檔 → 40 檔（預算仍充足）
3. 提高檢查頻率：10 秒 → 7 秒（更即時）

### 中期改進（2-4 週）
1. 加入新的異常檢測維度（技術指標）
2. 優化檢測算法（降低假陽性）
3. 實現自動學習（根據市場調整閾值）

### 長期改進（1 個月+）
1. 建立多市場監控系統（台股、港股、美股）
2. 集成其他信號源（新聞、資金流）
3. 實現自動交易推薦
```
