# 蜂群覺醒 — 多股票實時監控定義書

> **故事背景**：散戶面臨「眼睛跟不上市場」的困境。你需要一個永遠在線、不知疲倦的監控系統，實時發現異常波動並告警。
>
> 👉 [Substack 完整故事](https://aiagentcommander.substack.com/p/swarm-01) — 了解為什麼需要蜂群監控

## 一、問題定義

### 1.1 問題陳述

**核心問題**：
實時監控指定的股票池（5-100 檔），自動檢測價格異常波動（>5%），
並按照優先級分類發出告警，幫助投資者不遺漏任何機會。

**具體場景**：
- 散戶持有 20-30 檔自選股
- 無法 24/7 盯盤
- 需要秒級反應時間（< 10 秒告警）
- 希望按風險等級分類（Critical > Warning > Info）

### 1.2 背景與約束

**背景**：
- 市場開盤時 1 秒內可能發生 5-10% 的波動
- 人工監控容易遺漏（反應時間 > 30 秒）
- 散戶需要低成本、自動化的監控方案
- 告警規則因人而異（保守派 vs 激進派）

**約束條件**：
- 只監控價格數據，不做預測或推薦
- 不能修改或篡改股票行情數據
- 監控規則應該易於自定義
- 系統應該能處理網絡延遲和數據缺失

### 1.3 輸入與輸出

**輸入**：
- 類型：股票代碼列表 + 監控參數
- 規模：5-100 檔股票
- 格式：CSV、JSON 或純文本
- 示例：
  ```
  TSMC, NVDA, AAPL, GOOGL, META
  或
  {
    "stocks": ["2330.TW", "NVDA", "AAPL"],
    "alert_thresholds": {"critical": 10, "warning": 5},
    "check_interval": 10
  }
  ```

**輸出**：
- 類型：異常告警清單 + 監控報告
- 格式：JSON 結構化數據 + Markdown 報告
- 關鍵信息：
  - 股票代碼
  - 異常類型（漲停、跳空、異常成交量等）
  - 波動幅度（正確的百分比）
  - 時間戳
  - 優先級（Critical / Warning / Info）
  - 相關數據（現價、成交量、技術指標）
- 示例：
  ```json
  {
    "timestamp": "2026-06-04T09:35:42Z",
    "alerts": [
      {
        "stock": "TSMC",
        "type": "price_surge",
        "change": "+12.5%",
        "priority": "critical",
        "current_price": 1245.5,
        "volume_change": "+250%"
      }
    ]
  }
  ```

## 二、驗證標準

### 2.1 成功指標

| # | 指標 | 衡量方式 | 目標 | 為什麼重要 |
|---|------|--------|------|----------|
| 1 | **檢測靈敏度** | 自動檢測出的異常 ÷ 實際發生的異常數 | ≥ 95% | 不能遺漏重要機會 |
| 2 | **誤報率** | 誤報數 ÷ 總報數 | ≤ 5% | 避免假告警干擾 |
| 3 | **反應延遲** | 從異動發生到告警的時間 | < 10 秒 | 實時性要求 |
| 4 | **監控穩定性** | 無中斷監控的時間百分比 | ≥ 99% | 不能掉線 |
| 5 | **成本控制** | 實際成本 ÷ 預定預算 | ≤ 100% | 預算不超支 |
| 6 | **數據準確性** | 報告中的數據與真實行情一致 | 100% | 決策依據必須準確 |

**指標說明**：

- **檢測靈敏度 ≥ 95%**：
  假設一天有 20 個真實異常，應該至少檢測到 19 個（20 × 95%）

- **誤報率 ≤ 5%**：
  假設一天發出 100 條告警，其中最多 5 條是誤報

- **反應延遲 < 10 秒**：
  股票價格變化 1 秒內完成，監控系統應在 10 秒內發出告警

- **監控穩定性 ≥ 99%**：
  24 小時 = 86400 秒，最多允許中斷 864 秒（14.4 分鐘）

### 2.2 驗收條件

執行完成後，應滿足以下所有條件：

- [ ] **功能完整性**
  - [ ] 能監控指定的全部股票（無遺漏）
  - [ ] 能檢測所有定義的異常類型（漲停、跳空、異常成交量等）
  - [ ] 能按優先級排序告警（Critical > Warning > Info）

- [ ] **數據準確性**
  - [ ] 告警信息清晰（股票名、異常類型、波動幅度、時間）
  - [ ] 價格數據與真實行情一致
  - [ ] 成交量數據準確無誤

- [ ] **告警質量**
  - [ ] 檢測靈敏度 ≥ 95%
  - [ ] 誤報率 ≤ 5%

- [ ] **性能指標**
  - [ ] 反應延遲 < 10 秒
  - [ ] 監控穩定性 ≥ 99%

- [ ] **可用性**
  - [ ] 系統能 24/7 運行
  - [ ] 告警能立即發送（無延遲）

- [ ] **成本控制**
  - [ ] 實際成本 ≤ 預定預算
  - [ ] 成本在預定預算 ±10% 範圍內

### 2.3 失敗標準（什麼時候停止或升級）

- **若檢測靈敏度 < 90%**
  → 升級給交易員進行人工驗證
  → 提供：漏報的異常列表、原因分析、改進建議

- **若誤報率 > 10%**
  → 調整告警規則（降低敏感度或增加過濾條件）
  → 重新執行

- **若反應延遲 > 30 秒**
  → 升級給運維，診斷網絡或系統瓶頸
  → 提供：延遲日誌、性能分析

- **若監控中斷 > 1 分鐘**
  → 發出「監控中斷」告警
  → 嘗試自動恢復
  → 若 5 分鐘內無法恢復，升級給系統管理員

- **若成本超過預算 20%**
  → 停止，返回已完成的監控結果
  → 升級給項目經理，決策是否增加預算

## 三、執行策略

### 3.1 目標陳述

**最終目標**：
構建一個 7 × 24 自動監控系統，能實時發現股票價格異常波動，
按優先級分類告警，幫助投資者不遺漏任何交易機會，同時保持高的準確率和低的誤報率。

### 3.2 執行思路

**核心邏輯**（由 Claude Code 自動決定具體實現方式）：

```
1️⃣ 數據采集
   並行獲取所有股票的實時數據
   （哪些數據源、並行策略 → Claude Code 決定）

2️⃣ 異常檢測
   檢查每個股票是否存在異常波動
   （檢查維度、檢查順序、並行數量 → Claude Code 決定）

3️⃣ 優先級分類
   根據波動幅度和類型分類告警
   （分類規則、優先級算法 → Claude Code 決定）

4️⃣ 告警生成
   生成結構化的告警信息
   （告警格式、通知方式 → Claude Code 決定）

5️⃣ 報告生成
   匯總執行結果和統計信息
   （報告格式、統計維度 → Claude Code 決定）
```

**不涉及技術細節**：
- ❌ 不指定用幾個 Agent
- ❌ 不指定用什麼 API 或數據源
- ❌ 不指定並行還是串行
- ❌ 不設計系統架構

→ **所有技術決策由 Claude Code 自動決定**

### 3.3 限制條件

**系統邊界**：
- 只監控價格數據，不做預測
- 不能修改或篡改原始行情數據
- 不做投資建議（只提供數據和告警）
- 不涉及真實交易執行

**性能邊界**：
- 監控應該儘量並行（快速檢查所有股票）
- 但不要超過 10 個並行檢查（防止 API 限流）
- 告警應該立即發送，不能排隊延遲

**數據邊界**：
- 只使用公開的股票行情數據
- 不能使用非授權的數據源
- 如果某個股票無法獲取數據，應該跳過並記錄

**運維邊界**：
- 系統應該能在網絡不穩定的環境運行
- 應該有故障恢復機制（自動重連、重試）
- 應該有詳細的日誌記錄

### 3.4 決策規則

**決策規則**定義「在什麼情況下應該怎麼做」（Claude Code 自動執行）：

#### 規則 1：波動幅度分級
```
若 波動幅度 > 10%
→ 優先級：Critical（立即告警，紅色標記）
→ 行動：優先報告，觸發高頻告警

若 波動幅度 5-10%
→ 優先級：Warning（即時告警，黃色標記）
→ 行動：集合告警，正常頻率

若 波動幅度 < 5%
→ 優先級：Info（記錄，不告警）
→ 行動：只在報告中記錄，不發送即時通知
```

#### 規則 2：異常類型優先級
```
若 異常類型 = 漲停/跌停
→ 最高優先級：Critical
→ 行動：立即告警 + 發送多渠道通知

若 異常類型 = 成交量異常 (> 200%)
→ 優先級：Warning
→ 行動：立即告警

若 異常類型 = 正常波動
→ 優先級：Info
→ 行動：僅記錄
```

#### 規則 3：無法驗證的情況
```
若 無法獲取實時數據（網絡延遲）
→ 使用最後一次已知的數據
→ 標記為「延遲數據」
→ 不影響後續檢查

若 某個股票無法驗證
→ 標記為「無法監控」
→ 跳過此股票，繼續監控其他

若 檢測結果不確定（置信度 < 70%）
→ 標記為「待確認」
→ 升級給人工驗證
```

#### 規則 4：監控中斷処理
```
若 監控中斷 < 30 秒
→ 自動恢復，無需告警

若 監控中斷 30 秒 - 1 分鐘
→ 發出「監控中斷」告警
→ 嘗試自動恢復

若 監控中斷 > 1 分鐘
→ 發出「監控故障」告警（Priority: Critical）
→ 升級給系統管理員
```

#### 規則 5：成本和性能權衡
```
若 Token 消耗達到 80%
→ 進入節省模式
→ 降低檢查頻率：從 10 秒改為 30 秒
→ 保留核心監控功能

若 Token 消耗達到 100%
→ 返回已有的監控結果
→ 標記為「PARTIAL_COMPLETION」
→ 停止進一步檢查
```

### 3.5 降級與升級條件

#### 降級條件（自動簡化，繼續運行）

**情況 1：Token 消耗達到 80%**
- 降級方向：降低監控頻率
- 具體做法：
  - 從每 10 秒監控一次改為每 30 秒
  - 效果：成本降低 60%
  - 風險：可能遺漏快速波動（但保留關鍵信號）
- 標記：`DEGRADED_MODE` 記錄在報告中

**情況 2：某個股票無法獲取實時數據**
- 降級方向：使用備用數據
- 具體做法：
  - 使用上一次已知的數據
  - 或使用延遲 1-2 分鐘的行情數據
  - 但標記為「延遲」或「缓存」
- 標記：`CACHE_DATA` 記錄在報告中

**情況 3：API 請求超時**
- 降級方向：重試或跳過
- 具體做法：
  - 第 1 次超時：重試一次
  - 第 2 次超時：跳過此股票，繼續監控其他
  - 標記為「超時」
- 標記：`TIMEOUT` 記錄在報告中

**降級的優先級**：
```
優先級 1 - 保留核心功能：
  必須監控所有股票（不能遺漏）
  必須檢測 Critical 級別異常

優先級 2 - 可以降級：
  降低檢查頻率（10 秒 → 30 秒）
  使用緩存數據（實時 → 延遲）

優先級 3 - 最後降級：
  跳過低優先級股票
  只監控核心持倉
```

#### 升級條件（需要人工介入）

**情況 1：檢測靈敏度異常低**
- 條件：檢測靈敏度 < 90%
- 升級給：交易員或數據分析師
- 提供信息：
  - 漏報的異常列表（哪些異常被遺漏了）
  - 原因分析（為什麼漏報）
  - 改進建議（怎麼提高靈敏度）
- 標記：`ESCALATED_TO_TRADER`

**情況 2：誤報率過高**
- 條件：誤報率 > 10%
- 升級給：系統管理員（調整告警規則）
- 提供信息：
  - 誤報的異常列表
  - 誤報的原因分析
  - 建議的規則調整
- 標記：`ESCALATED_TO_ADMIN`

**情況 3：異常無法判斷**
- 條件：檢測到異常但置信度 < 70%
- 升級給：交易員（人工驗證）
- 提供信息：
  - 異常詳情
  - 置信度分數
  - 建議的判斷方向
- 標記：`ESCALATED_UNCERTAIN`

**情況 4：系統故障或監控中斷**
- 條件：監控中斷 > 1 分鐘無法恢復
- 升級給：系統管理員
- 提供信息：
  - 故障時間和持續時間
  - 故障日誌
  - 影響的股票列表
- 標記：`ESCALATED_SYSTEM_FAILURE`

**情況 5：成本超支**
- 條件：預期成本超過預算 20%
- 升級給：項目經理
- 提供信息：
  - 當前成本和預定預算
  - 成本超支原因
  - 已完成的監控範圍
  - 建議的解決方案
- 標記：`ESCALATED_COST_OVERRUN`

**升級的級別**：
```
Level 1 - 低優先級升級（24 小時內處理）：
  檢測靈敏度低
  誤報率高

Level 2 - 中優先級升級（2 小時內處理）：
  異常無法判斷
  監控性能下降

Level 3 - 高優先級升級（立即處理）：
  系統故障、監控中斷
  成本嚴重超支（> 50%）
```

```

預期成本：       0.12 單位 = 120 萬 Token ≈ $1-3（美金）
應急預留：       0.18 單位 = 180 萬 Token ≈ $1-5（美金）
```

**這意味著什麼**：
- ✅ 用 Claude Code 完成一個複雜的投資監控系統，成本只有幾美金
- ✅ 相比之下，人工完成相同任務需要 40-50 小時工時
- ✅ 時間成本節省：98%
- ✅ 金錢成本：便宜得令人吃驚

### 4.2 成本估算邏輯

**輸入規模**：
- 股票數量：20 檔
- 監控頻率：每 10 秒檢查一次
- 監控時間：7 × 24 小時（持續運行）
- 每次檢查的複雜度：簡單（只檢查價格數據）

**複雜度分析**：
- ✅ 簡單（不涉及複雜計算、不涉及多維度分析）
- 使用輕量級模型（Haiku）充分
- 少量 API 調用和邏輯判斷

**成本估算**（參考數據）：

| 組件 | 單位成本 | 數量 | 小計 |
|------|--------|------|------|
| 實時監控（Haiku） | 0.0001 單位/檢查 | 1000 檢查 | 0.10 單位 |
| 異常檢測邏輯 | 0.0002 單位/檢查 | 1000 檢查 | 0.02 單位 |
| **總計** | | | **0.12 單位** |

**說明**：
- 一天 = 86400 秒
- 每 10 秒檢查一次 = 8640 檢查/天
- 我們估算 1000 檢查/執行 = 約 3 小時的監控數據
- 實際 24 小時監控會成倍增加，但預算中只包含一次完整執行

### 4.3 成本監控策略

**實時監控階段**：

| 成本階段 | 成本量 | 狀態 | 觸發行動 |
|---------|--------|------|---------|
| 正常運行 | 0 - 0.18 | 🟢 | 繼續全功能監控 |
| 警告閾值 | 0.18 - 0.24 | 🟡 | 進入節省模式 |
| 臨界點 | 0.24 - 0.30 | 🔴 | 返回已有結果 |
| 超出上限 | > 0.30 | 🛑 | 立即停止 |

**成本監控動作**：

當成本達到 **60%**（0.18 單位）：
- 發出「成本警告」
- 進入節省模式（降低檢查頻率）
- 但不影響關鍵功能

當成本達到 **80%**（0.24 單位）：
- 發出「成本臨界」告警
- 停止低優先級檢查
- 保留 Critical 和 Warning 級別告警

當成本達到 **100%**（0.30 單位）：
- 返回已完成的監控結果
- 標記為「PARTIAL_COMPLETION」
- 停止進一步檢查

### 4.4 成本優化建議

**根據執行結果調整**：

執行後分析實際成本：

| 情況 | 實際 vs 預定 | 優化建議 |
|------|-----------|--------|
| 實際成本 < 預期 30% | 遠低於預期 | 可以擴大監控範圍（增加股票數或檢查頻率） |
| 實際成本 = 預期 ±10% | 符合預期 | 維持現狀，已是最優配置 |
| 實際成本 > 預期 10% | 高於預期 | 調整監控頻率（10 秒 → 15-20 秒） |
| 實際成本 > 預期 30% | 大幅超期 | 評估是否需要增加總預算 |

**長期優化機制**：

如果發現：
- 某個股票很少異常 → 降低其檢查頻率
- 某個時段異常集中（如開盤前 5 分鐘） → 只在該時段提高檢查頻率
- 大多數異常出現在交易時段 → 平時監控可以降頻
